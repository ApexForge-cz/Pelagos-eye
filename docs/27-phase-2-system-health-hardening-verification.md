# Phase 2 system-health hardening verification

- Verification date: 2026-09-19
- Scope: issue `#16`; `GET /system/status` only
- Schema migrations: none
- Frontend changes: none

## Implemented contract

`GET /system/status` now reports API version and check time, PostGIS connectivity, Redis
connectivity, and a bounded summary for every source registered in the existing catalog.
Each provider summary contains the controlled source state, availability, freshness age
and thresholds, effective cache age, source publication/retrieval time, and the latest
ingestion run's status, source state, UTC start/finish times, and received/accepted/rejected
record counts.

PostGIS and Redis use `LIVE` or `OFFLINE` dependency states. A missing configuration,
timeout, connection error, or unusable URL returns Redis `OFFLINE` / `DATA UNAVAILABLE`;
the probe has one-second connect/read timeouts and never exposes the configured URL. Redis
failure does not fabricate data and does not prevent PostGIS-backed provider summaries.
The overall API state is `READY` only when both PostGIS and Redis probes succeed.

Provider state continues to use the existing source-specific `LIVE`, `CACHED`, `DELAYED`,
and `OFFLINE` freshness policy. It is computed from stored verified ingestion evidence;
the health request does not call upstream providers. A live database with no registered
sources returns an empty provider list. If PostGIS is unavailable, the dependency is
`OFFLINE` and provider state is unavailable. `NO COVERAGE` remains a record-query outcome,
not a provider health state.

## Remaining boundary

The endpoint does not schedule ingestion, actively contact upstream providers, report a
worker queue that does not yet exist, or convert `NO COVERAGE` into a source state. The
fresh Compose database intentionally contained no imported provider records; provider and
latest-ingestion fields remain covered by the focused service and API tests rather than by
fabricated integration data.
