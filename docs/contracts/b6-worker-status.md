# B6 Live AIS worker status contract

**Status:** Design contract for B6.1 worker supervision. This document does not
authorize a public route, frontend integration, persistence, replay, or a Phase 4
completion claim.

## Scope

This contract describes the non-sensitive status and continuity events emitted by
the single backend Pelyr worker. The worker uses the fixed Gulf of Finland
subscription, Pelyr `/v1`, and `fields=position` only. Accepted position frames
are passed to the already accepted B5 normalizer.

The worker must never place API keys, raw provider frames, MMSI values,
coordinates, or full provider envelopes in status events, metrics, or logs.

## Independent dimensions

These dimensions must not be collapsed into one boolean:

| Dimension | Values | Meaning |
| --- | --- | --- |
| Transport connection | `CONNECTING`, `CONNECTED`, `RECONNECTING`, `DISCONNECTED` | State of the single upstream socket |
| Source freshness | `LIVE`, `DELAYED`, `OFFLINE` | Age of the most recent accepted provider evidence |
| Availability | `AVAILABLE`, `DATA UNAVAILABLE` | Whether the worker can currently provide normalized observations |
| Coverage | `COVERED`, `NO COVERAGE` | Whether the fixed configured region has reviewed provider coverage; not vessel count |
| Content label | `MODEL DATA`, `DERIVED`, `TEST DATA` | Content classification when applicable; live provider positions are not any of these labels |

`CONNECTED` does not prove `COVERED`, and an empty covered result is not
`NO COVERAGE`. A provider failure is `DATA UNAVAILABLE`, not zero vessels.

## Worker state transitions

The worker follows this bounded sequence:

1. `DISCONNECTED` -> `CONNECTING` when a start or bounded reconnect begins.
2. `CONNECTING` -> `CONNECTED` only after the protocol, effective limits, and
   `welcome.sources[]` have passed validation and the fixed subscription is accepted.
3. `CONNECTED` -> `RECONNECTING` on socket close, provider rejection, malformed
   control frame, heartbeat timeout, or an invalid source/licence observation.
4. `RECONNECTING` -> `CONNECTING` after capped exponential backoff with bounded
   jitter. There is never more than one active connection attempt.
5. Any state -> `DISCONNECTED` on cancellation or clean shutdown.

The worker emits a continuity gap whenever an upstream connection or stream epoch
ends. The gap is not replayable and does not permit interpolation across silence.

## Event envelope

Every event is internal worker telemetry and uses a timezone-aware UTC timestamp:

```json
{
  "event": "worker.status",
  "occurred_at": "2026-09-23T00:00:00Z",
  "connection_state": "RECONNECTING",
  "freshness": "OFFLINE",
  "availability": "DATA UNAVAILABLE",
  "reason": "heartbeat_timeout",
  "reconnect_attempt": 2,
  "stream_epoch": "opaque-epoch",
  "replay_available": false
}
```

`stream_epoch` is an opaque identifier generated by the worker. It must not embed
credentials, raw provider data, MMSI, or coordinates. `reason` is a bounded enum,
not an exception string or raw provider message.

Allowed status reasons include:

- `startup`
- `welcome_accepted`
- `provider_rejected`
- `malformed_control_frame`
- `source_directory_invalid`
- `licence_invalid`
- `heartbeat_timeout`
- `feed_loss`
- `socket_closed`
- `backoff_wait`
- `shutdown`

## Gap event

On every continuity break, emit one bounded gap event:

```json
{
  "event": "stream.gap",
  "occurred_at": "2026-09-23T00:00:00Z",
  "stream_epoch": "opaque-epoch",
  "reason": "heartbeat_timeout",
  "replay_available": false
}
```

The event carries no raw frame, position, vessel identifier, or secret. A later
consumer must request a fresh snapshot after a new epoch; it must not infer a
continuous track from pre-gap and post-gap positions.

## B6.1 and B6.2 boundary

### B6.1 worker supervision

B6.1 owns the upstream connection, fixed subscription enforcement, welcome/source
validation, heartbeat/feed/loss monitoring, bounded reconnect backoff, cancellation,
and these non-sensitive status/gap events.

### B6.2 fan-out and backpressure

B6.2 owns normalized in-memory delivery queues, same-MMSI coalescing, sequence and
epoch assignment for product delivery, slow-client policy, queue overflow gaps, and
load tests. It must consume B6.1 status/events rather than duplicate provider
connection logic.

Neither stage authorizes a browser-to-Pelyr connection, durable live-AIS storage,
replay, export, dynamic bounds, or a public WebSocket by itself.

## Test requirements

Tests must use fictional `TEST DATA` or mocked transport only and verify:

- valid welcome/effective-limit/source-directory acceptance;
- each rejection reason above without raw payload leakage;
- heartbeat success, timeout, feed loss, and dropped-count reporting;
- capped backoff and no parallel connection attempts;
- cancellation leaves no background task;
- every continuity break emits `replay_available = false`;
- missing data remains `DATA UNAVAILABLE`, never zero-filled.
